# Task contract: user-selectable detection presets

Date: 2026-10-10  Dispatch: one agent
Request as given: "maybe we allow user to select from several combos of
settings and they can pick and choose based on the data they have. i don't
think there's going to be one set of rules that does a good job with
everything"

## Intent and scope

No single rule set suits every schema. Measured on public data, the strict
rules take Chinook precision from 14.7 to 31.0 percent and FAERS from 12.3 to
50.0 percent, while dropping recall from 90.9 to 81.8 and from 100.0 to 75.0.
A conventionally named schema wants the strict rules; a legacy extract with
names like `primaryid` and `supportrepid` wants the permissive ones.

In scope: named presets in the sidebar that bundle the existing signal toggles
and the new rules, the plumbing that records which preset produced a scan, and
showing each preset's measured recall and precision so the choice is made on
evidence rather than on the names.

Users are reviewers choosing how to scan a schema they have just loaded.

## Non-goals

- No new detection rules and no changes to scoring. Do not touch
  `R/utils_inference.R` except to read settings that already exist. The
  containment signal is the other contract and may land before or after this
  one.
- Do not change the meaning of any existing toggle, only which combinations a
  preset selects.
- Do not remove the existing "Signal toggles" controls; the Custom preset
  reveals them.
- No change to `detect_shared_columns()` or the shared-columns section.
- No reformatting, no Air run. Do not merge, open a pull request, or delete
  branches.

## Context

- R package `tableexplorer`, Shiny. The sidebar already has a detection method
  selector, a minimum confidence selector, "Detect composite keys", a
  relationships-to-show selector and a "Signal toggles" group
  (`R/mod_detection.R`). `detection$detection_settings_rv()` and
  `detection$scan_request_rv()` carry those settings into `R/app_server.R`,
  which calls `detect_fks()` with `enable_flags`.
- The scan is cached per request id. Changing a setting does not rescan on its
  own: the user presses Run Detection.
- `R/utils_inference.R` holds the rules a preset switches between: the
  naming tiers, the parent-must-be-a-key fallback, the chance-overlap discount
  (`overlap_expected_by_chance`, `overlap_chance_max_distinct`), the
  cardinality floor (`cardinality_min_distinct`) and the possible-key names
  (`is_possible_key_name`). Several are currently unconditional rather than
  settings.
- Measurement harness: `dev/fixtures/public/fetch.R` and
  `dev/fixtures/public/score_public.R chinook faers`, which reads whole tables
  and prints tables, rows, truth, found, hit, recall, precision and seconds.
  Chinook and FAERS are in the user cache already.
- Session export and restore carry detection settings; see `R/mod_export.R`
  and `R/utils_export.R`.
- R is at "C:\Program Files\R\R-4.6.1\bin\Rscript.exe". Never run `Rscript -e`
  with inline code: spaced paths segfault. Put code in a file.
- Verification: `RENV_CONFIG_AUTOLOADER_ENABLED=FALSE "C:\Program Files\R\R-4.6.1\bin\Rscript.exe" dev/check.R`

## Constraints

- Presets set existing knobs. A preset must be expressible as a set of
  settings, so that Custom can reproduce any preset exactly.
- The default preset reproduces today's behaviour on the branch it lands on,
  so merging this changes nothing until a user picks another preset.
- A scan records which preset produced it, and that travels into the
  Relationships tab, the data dictionary and the exports. A file of links
  whose rules are unknown cannot be interpreted later.
- The numbers shown next to a preset are measured, never estimated, and carry
  the date and the dataset they came from. They are generated by the harness
  into a data file, not typed by hand.
- Changing the preset does not rescan on its own: the user presses Run
  Detection, as now.
- Tests exercise behaviour, one per behaviour, each able to fail. Follow the
  `shiny::testServer` pattern in `tests/testthat/test-relationships.R`.
- No em dash (U+2014) anywhere, including commit messages.
- A script must not write a file before all its assertions have passed.
- Stop and report rather than deciding alone when: a preset cannot be
  expressed as settings without changing a rule's meaning, or the default
  preset changes any measured number.

## Edge cases

- **A setting changed by hand after a preset is chosen**: the selector shows
  Custom, and the scan records Custom plus the settings, not the preset it
  started from.
- **A session restored from an export written before presets existed**: treat
  as Custom with the settings it carries, and say so rather than guessing a
  preset.
- **A preset whose measured numbers are missing** (dataset never fetched):
  show the preset with no numbers and say they have not been measured, rather
  than hiding it or showing a guess.
- **Numbers measured on a different version of the rules**: stamp the data
  file with the commit it was measured at, and say when the stamp does not
  match the running build.
- **Scan still running when the preset changes**: the recorded preset is the
  one the scan started with.

## Output requirements

- Presets in the sidebar near the detection method, with a one-line
  description each and the measured numbers under the name.
- Proposed presets, to be confirmed: `<preset list>`.
- A data file under `dev/fixtures/public/` holding the measured numbers, with
  the dataset, date and commit, generated by the harness.
- The preset name appears on the Relationships tab beside the counts, in the
  data dictionary YAML, and in the session export.
- Logical commits, push the branch, no pull request.

## Acceptance and evidence

   `real: 157 of 157`, `false: 0`.
2. With the default preset selected, `score_public.R chinook faers` reports
   the same recall and precision as the branch did before this change, to one
   decimal place.
3. Selecting the most permissive preset and re-running the harness produces
   higher recall on FAERS than the default preset does, measured, with both

4. A `testServer` test: choosing a preset sets the expected settings, and
   changing one setting afterwards reports the preset as Custom.
5. A test that the preset name reaches the session export and the data
   dictionary.
6. A test that a session restored without a preset reports Custom rather than
   inventing one.

## Open assumptions

- `<preset list>`: proposed four. **Conventional names** (strict rules, for
  Rails, Django or Access-style schemas), **Balanced** (default, strict rules
  plus possible-key names and containment), **Unconventional names** (chance
  discount softened or off, containment weighted up, low confidence shown),
  **Custom** (reveals the individual toggles).
- Which preset is the default: proposed Balanced, on the condition in
  Constraints that the default reproduces current behaviour. If Balanced does
  not reproduce it, the default is whichever preset does, and Balanced is
  offered second.
- Whether the rules currently hard-coded (chance discount, cardinality floor,
  possible-key names) become settings in this contract, or stay fixed with
  presets only selecting among existing toggles. Proposed: they become
  settings, since otherwise the presets cannot differ in the ways that matter.
- Whether presets are per session only, or remembered between sessions.
  Proposed: per session, recorded in the export, not remembered otherwise.

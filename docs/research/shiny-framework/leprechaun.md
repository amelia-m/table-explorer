# leprechaun

Agent A report for the Shiny framework research contract. Checked 2026-10-02.
Covers leprechaun only; golem appears only where leprechaun compares itself to
it, or to name the golem counterpart of a leprechaun function.

## What it is

leprechaun is a code generator for Shiny apps built as R packages. You create a
package first (`usethis::create_package()`), then run `leprechaun::scaffold()`
inside it [1][4]. Its own docs position it against golem: "Golem is a great
package" but it "comes with numerous features not always required" and "adds
dependencies to my application"; leprechaun instead "generates code and does not
make itself a dependency of the application you build" and offers "a family of
functions to selectively add" features [3]. Frigaard's Shiny App-Packages book
(opinion, 2025-04-22) calls it "golem a la carte" [10].

## What it generates or requires

`scaffold(ui = c("navbarPage", "fluidPage"), bs_version = bootstrap_version(), overwrite = FALSE)` [11][12] writes:

- `R/ui.R` (`ui()` plus `assets()`), `R/server.R`, `R/run.R` (exported
  `run(...)` that calls `shinyApp(ui, server, ...)`, and internal `run_dev()`) [13][14]
- `R/assets.R` (`serveAssets()`), `R/leprechaun-utils.R`
  (`make_send_message()`), `R/input-handlers.R`, `R/zzz.R` (an `.onLoad` that
  maps `img` to `inst/img`), `R/_disable_autoload.R` [14][15][16]
- `inst/assets/`, `inst/img/`, `inst/dev/`, and `inst/run/app.R` (the dev
  launcher: `leprechaun::build()`, then `pkgload::load_all()`, then `run()`) [14][17]
- a `.leprechaun` lock file recording the version and features used, added to
  `.Rbuildignore` [12][18]

Files carry a "DO NOT EDIT THIS FILE" banner where leprechaun expects to
regenerate them [15][16].

`serveAssets()` lists every `.js` and `.css` file anywhere in the installed
package (`list.files(system.file(package = ...), recursive = TRUE)`) and wraps
them in one `htmlDependency` [15]. Placement inside `inst/` does not scope it;
only the `ignore` argument does, and that argument is in the dev version (with
a 2025 fix) [6][15].

Opt-in features, each adding files and often a dependency [19][20]:

| leprechaun function | Adds | Nearest golem counterpart [2] |
|---|---|---|
| `scaffold()` | full skeleton above | `create_golem()` |
| `add_module(name)` | `R/module_<name>.R` with `<name>UI()` and `<name>_server()` | `add_module()` |
| `add_app_file()` | root `app.R` from `inst/run/prod.R`, build-ignored | `add_positconnect_file()` |
| `use_config()` | `R/config.R`, `inst/config.yml`; yaml to Imports | generated `get_golem_config()` |
| `use_sass()` | `scss/`, `inst/dev/sass.R`; sass to Suggests | `add_sass_file()` |
| `use_packer()` | `inst/dev/packer.R`; packer to Suggests | none (golem has `add_js_file()`) |
| `use_js_utils()` | `srcjs/leprechaun-utils.js`, `R/utils-js.R` | golem's built-in JS handlers |
| `use_html_utils()` | `R/html-utils.R`; htmltools to Imports | `use_utils_ui()` |
| `use_endpoints_utils()` | `R/endpoint-utils.R`; jsonlite to Imports | none |
| `build()`, `build_roclet()` | runs `inst/dev/*.R` scripts (sass, packer) | none |
| `sitrep()`, `update_scaffold()` | compare and regenerate templates against the lock file | none |
| `create_assets()`, `create_onload()`, `create_utils()`, `create_input_handlers()`, `bootstrap_version()` | regenerate single scaffold files; report the Bootstrap version | none |

The guide says `use_config()` creates `inst/config.R` [19]; the code writes
`R/config.R` [20]. The code is taken as correct.

Not provided by leprechaun: an options-passing wrapper like
`with_golem_options()`/`get_golem_options()`, a `system.file()` helper like
golem's `app_sys()`, `add_resource_path()` (it hard-codes `img` in `zzz.R`),
favicon helpers, Dockerfile or CI generators, and test helpers [11][14].

## Runtime vs dev-time dependencies

Verified from the generator's code, not marketing text:

- Runtime (added to the app's Imports by `scaffold()`): shiny, bslib, htmltools [12].
- Added to the app's Suggests: pkgload [12]. But the deploy `app.R` from
  `add_app_file()` calls `pkgload::load_all()` [17][21], so any server that runs
  that file needs pkgload installed. In practice it is a deploy-time runtime
  dependency.
- Opt-in runtime: yaml (`use_config()`), jsonlite (`use_endpoints_utils()`) [20].
- Dev only: leprechaun itself, sass and packer (Suggests, used by `build()`),
  plus node/npm if packer is used [19][20].

The "does not become a dependency" claim holds for the installed package. It
does not hold for `inst/run/app.R`, which calls `leprechaun::build()` [17], so
`run_dev()` needs leprechaun installed.

## Config handling

`use_config()` adds `config_read()` (reads `inst/config.yml` via
`yaml::read_yaml(system.file(...))`) and `config_get(value, config = NULL)`
[22]. The template yml is one line, `production: true` [23]. There are no
environment profiles and no override via env var, unlike golem config built on
the config package [unverified for the golem side; see golem.md]. Nothing applies
config values to Shiny options automatically: for table-explorer,
`shiny.maxRequestSize` would still need an explicit `options()` call in
`run()` or `server()`. The plumbing is about 25 lines that the project owns
outright.

## Testing story

leprechaun generates no tests and no test helpers [11][14]. Because the output
is an ordinary package, testthat, `shiny::testServer()` and shinytest2 apply as
for any package app (Frigaard, opinion) [10]. Open issue #14 (2024-04-08, no
reply) reports `shinytest2::record_test()` failing on a leprechaun app because
`serveAssets()` was not found during app start [24]. Not reproduced here.
Open issue #21 reports that `run_dev()` changes the working directory to
`inst/run`, which breaks relative file paths [25].

## Fit with each shipping route

- **R package:** native; every leprechaun app is a package [11]. The scaffold
  adds `.leprechaun`, `scss` and the root `app.R` to `.Rbuildignore`
  [12][19][21]. Whether `R/_disable_autoload.R` or the `inst/dev` and
  `inst/run` scripts raise `R CMD check` notes was not tested [unverified].
  leprechaun's own CRAN checks pass, but that says nothing about apps it
  generates.
- **Positron extension:** leprechaun has no Positron or VS Code tooling. The
  third-party shinyframeworks extension supports basic Shiny, rhino and golem,
  and asked for leprechaun support in issue #16 (2025-01-20); no reply [26].
  How an app ships inside an extension is Agent C's question; leprechaun's
  output is a plain package, so it neither helps nor blocks that.
- **Posit Connect Cloud:** `add_app_file()` writes the root `app.R` documented
  as "required to run on RStudio Connect, RStudio server, and shinyapps.io"
  [21]; it sources the package with `pkgload::load_all()` [17]. Connect Cloud is
  not named in leprechaun's docs. table-explorer's current `app.R` already uses
  the same `load_all()` pattern, so this route is no different from today.

## renv interplay

No renv support in leprechaun: no renv-aware Dockerfile, no lockfile helpers
[11]. Because `inst/run/app.R` calls `leprechaun::build()` and the root `app.R`
calls `pkgload::load_all()`, a code-scanning tool such as
`renv::dependencies()` would likely record leprechaun and pkgload as project
dependencies [unverified]. The `.leprechaun` lock file tracks generator
versions, not package versions; it is unrelated to `renv.lock` [18].

## Notable limits or open issues

- Dormant: last CRAN release 2022-01-19; asset-ignore fix only on GitHub [1][6].
- `serveAssets()` loads every `.js`/`.css` in the installed package [15], and
  issues #8 ("serveAssets ignores all assets"), #11 (`type = module` not added)
  and #19 (launch fails with more than one `inst/assets/*.js`, 2025-07-15) are
  open [8]. table-explorer ships `inst/app/www/vendor/` scripts, so this
  matters.
- `scaffold()` overwrites an existing `R/zzz.R` (issue #12) [8].
- Fixed names: `ui()`, `server()`, `run()`, `module_<name>.R`, `<name>UI()`,
  `<name>_server()` [13][28]. table-explorer uses `app_ui`, `app_server`,
  `run_app()` and `mod_*.R`, so adopting it means renames or hand edits that
  `update_scaffold()` may later overwrite.
- Bootstrap version is fixed in the lock file at scaffold time [6].
